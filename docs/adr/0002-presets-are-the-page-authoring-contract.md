# Presets are the page-authoring contract

Page structure is authored in TypeScript, not in Payload: a Preset is a factory from named
arguments to a `SectionDefinition`, and it is the only vocabulary both code and the CMS use.
Payload stores a preset invocation — the preset's name plus its arguments — rather than an
expanded section tree, so there is one authoring surface instead of two that can drift.

## Status

accepted

## Considered options

- **CMS-first** — Payload blocks as the schema, `SectionDefinition` as generated mapper output.
  Rejected, though it is what `CLAUDE.md` rule 1 otherwise implies.
- **Full `SectionDefinition` mirror in Payload** — maximum editor freedom over columns, gutters
  and spans. Rejected: the same schema maintained by hand in two places, awkward responsive
  fields in the admin UI, and editors free to build off-design pages.
- **Both, split by route group** — CMS for marketing routes, TypeScript for product routes.
  Rejected as two schemas guaranteed to drift.

The previous Qwik system already worked this way. Its `block-types.ts` header reads: *"derived
from design system component props (source of truth). Payload CMS configuration will be updated
to match these types."* That sync was manual and permanent; this ADR keeps the direction and
removes the manual step.

## Consequences

- **Contradicts `CLAUDE.md` rule 1** for the page layer specifically. Rule 1 carries an explicit
  carve-out: schema-first governs Payload *data*; design-system config types are hand-authored
  TypeScript from which Payload is derived.
- **One zod schema per preset is the single definition** of its arguments (ADR-0001). The
  TypeScript argument type comes from `z.infer`; the Payload block fields are generated by walking
  the same schema. We own that generator, and it only needs to cover the field types presets use.
  No off-the-shelf zod → Payload-fields package exists, but `zod-to-json-schema` is mature, so the
  likely shape is zod → JSON Schema → Payload fields with only the last hop bespoke.
- **The generator has a deadline, not a vibe.** Presets 1–3 get hand-written Payload blocks —
  drift risk is negligible at that scale and three real argument surfaces are what the generator
  should be designed against. **Preset 4 does not get a hand-written block**: the generator is a
  blocking prerequisite for it, and backfills the first three. Without a number here, "defer until
  the shape is stable" becomes fourteen hand-written blocks and an ADR describing something that
  does not exist.
- **Configs must stay JSON-serializable**, since they are stored in Payload. Behaviour is
  therefore expressed as a named Action resolved through a registry — see
  [ADR-0005](0005-behaviour-in-config-is-a-named-action.md).
- **Blocks survive as a second layer.** A Preset composes a Section; a Block fills a Column.
  Presets that intend free composition expose a `blocks[]` argument mapping to a Payload blocks
  field; the rest have fixed layouts. Collapsing the two would need a preset per
  layout × content combination.
- **Presets are the one idea the previous system never built** — it had nine copy-tweak
  `page-config.ts` fixtures and zero factories, so "formalize as presets" is inventing an API
  rather than transcribing one. Argument surfaces are therefore derived from the *target designs*
  and composed from shadcn primitives, per [ADR-0006](0006-shadcn-first-not-a-port.md).
